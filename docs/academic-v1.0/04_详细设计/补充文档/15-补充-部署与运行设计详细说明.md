## 2. 环境规划建议

### 2.1 环境划分
基于“内部试用但按正式系统标准要求”的原则，建议划分以下三个环境：

| 环境 | 用途 | 数据规模 | 访问权限 | 自动部署 |
|------|------|----------|----------|----------|
| **开发环境 (DEV)** | 开发人员日常开发、调试与联调 | 最小数据集（< 100所学校，< 1000名人才） | 开发团队内部访问 | 代码提交自动触发 |
| **测试环境 (TEST/UAT)** | 功能测试、集成测试、业务验收 | 中等数据集（约 500所学校，5000名人才） | 测试团队、业务试用方 | 手动触发或按版本发布 |
| **生产环境 (PROD)** | 正式内部试用 | 完整数据集（OpenAlex 学术人才数据） | 授权招聘团队 | 手动审批后发布 |

### 2.2 环境配置要求

#### 2.2.1 开发环境
- **服务器**：本地开发机或共享开发服务器
- **数据库**：PostgreSQL 14+（可容器化运行）
- **前端**：Vite 开发服务器 (localhost:2012)
- **后端**：FastAPI 开发服务器 (localhost:8000)
- **网络**：内网访问，无需公网暴露

#### 2.2.2 测试环境
- **服务器**：专用测试服务器（4核8G内存，100G存储）
- **数据库**：PostgreSQL 14+（独立实例）
- **部署方式**：Docker Compose 或直接进程部署
- **域名**：test-talent.内部域名（如有）
- **备份**：每日自动备份，保留7天

#### 2.2.3 生产环境
- **服务器**：专用生产服务器（8核16G内存，200G SSD存储）
- **数据库**：PostgreSQL 14+（主从架构预留，初期可单实例）
- **部署方式**：Docker Compose + systemd 托管
- **域名**：talent.内部域名
- **备份**：每日全量备份 + 实时WAL归档，保留30天

### 2.3 环境变量与配置管理
- 所有环境配置通过 `.env` 文件管理，不硬编码在代码中
- 敏感信息（数据库密码、API密钥）使用环境变量或专用配置服务
- 各环境配置模板：
  - `.env.dev` - 开发环境
  - `.env.test` - 测试环境
  - `.env.prod` - 生产环境

## 3. 部署单元建议

### 3.1 部署单元划分
根据技术栈冻结单（模块化单体架构），将系统划分为四个部署单元：

1. **前端 Web 应用** (frontend)
   - 技术栈：React 18 + TypeScript + Vite + Ant Design v5
   - 产出：静态文件（HTML、CSS、JS）
   - 部署：Nginx 静态文件服务

2. **后端 API 服务** (backend)
   - 技术栈：Python 3.11 + FastAPI + SQLAlchemy
   - 产出：RESTful API 服务
   - 部署：Uvicorn + Gunicorn 进程管理

3. **数据同步任务** (sync-worker)
   - 技术栈：Python 3.11 + SQLAlchemy + Alembic
   - 产出：定时/手动触发的数据同步任务
   - 部署：Celery（可选）或直接脚本 + systemd/cron

4. **数据库服务** (database)
   - 技术栈：PostgreSQL 14+
   - 部署：独立数据库实例

### 3.2 部署包结构
```
talent-platform-v1.0.0/
├── frontend/                    # 前端构建产物
│   ├── index.html
│   ├── assets/
│   └── ...
├── backend/                     # 后端部署包
│   ├── app/                    # FastAPI应用
│   ├── requirements.txt
│   ├── alembic/                # 数据库迁移
│   └── start.sh               # 启动脚本
├── sync-worker/                # 同步任务
│   ├── tasks/
│   ├── requirements.txt
│   └── run_sync.py
├── docker-compose.yml          # Docker编排文件
├── deploy.sh                   # 部署脚本
└── README.md                   # 部署说明
```

### 3.3 部署策略

#### 3.3.1 开发环境部署
```bash
# 前端开发
cd frontend && npm run dev

# 后端开发
cd backend && uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

#### 3.3.2 测试/生产环境部署
**方案A：Docker Compose（推荐）**
```yaml
version: '3.8'
services:
  postgres:
    image: postgres:14-alpine
    environment:
      POSTGRES_DB: talent_db
      POSTGRES_USER: talent_user
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - postgres_data:/var/lib/postgresql/data
      - ./init.sql:/docker-entrypoint-initdb.d/init.sql
    ports:
      - "5432:5432"

  backend:
    build: ./backend
    environment:
      DATABASE_URL: postgresql://talent_user:${DB_PASSWORD}@postgres:5432/talent_db
    ports:
      - "8000:8000"
    depends_on:
      - postgres

  frontend:
    build: ./frontend
    ports:
      - "80:80"
    depends_on:
      - backend
```

**方案B：传统进程部署**
1. 数据库：独立PostgreSQL实例
2. 后端：systemd服务管理（`talent-backend.service`）
3. 前端：Nginx静态文件服务 + 反向代理到后端API
4. 同步任务：systemd定时服务或cron作业

## 6. 监控与告警

### 6.1 监控指标体系

#### 6.1.1 基础设施监控
| 指标类别 | 具体指标 | 正常范围 | 告警阈值 |
|----------|----------|----------|----------|
| **服务器** | CPU使用率 | < 70% | > 85% 持续5分钟 |
| | 内存使用率 | < 80% | > 90% 持续5分钟 |
| | 磁盘使用率 | < 85% | > 90% |
| | 网络流量 | 无异常峰值 | 突发增长 > 300% |
| **数据库** | 连接数 | < 最大连接数80% | > 最大连接数90% |
| | 查询响应时间 | P95 < 500ms | P95 > 1000ms |
| | 锁等待时间 | < 100ms | > 500ms |

#### 6.1.2 应用性能监控
| 指标类别 | 具体指标 | 正常范围 | 告警阈值 |
|----------|----------|----------|----------|
| **后端API** | 请求成功率 | > 99% | < 95% |
| | 平均响应时间 | < 300ms | > 1000ms |
| | 错误率（4xx/5xx） | < 1% | > 5% |
| | 关键接口可用性 | 100% | < 99% |
| **前端** | 页面加载时间 | < 3秒 | > 5秒 |
| | JS错误数 | 0 | > 10次/小时 |
| | API调用成功率 | > 99% | < 95% |

#### 6.1.3 业务监控
| 指标类别 | 具体指标 | 正常范围 | 告警阈值 |
|----------|----------|----------|----------|
| **数据同步** | 同步任务成功率 | 100% | < 95% |
| | 同步延迟 | < 24小时 | > 48小时 |
| | 数据更新量 | 符合预期 | 连续3次为0 |
| **用户行为** | 活跃用户数 | > 0（工作日） | 连续24小时为0 |
| | 搜索成功率 | > 95% | < 80% |
| | 导出成功率 | 100% | < 90% |

### 6.2 监控工具建议

#### 6.2.1 免费/开源方案（第一阶段推荐）
- **基础设施监控**：Prometheus + Node Exporter + Grafana
- **应用性能监控**：Prometheus + 自定义指标 + Grafana
- **日志收集**：ELK Stack（Elasticsearch + Logstash + Kibana）或 Loki
- **前端监控**：Sentry（错误监控） + Web Vitals（性能监控）

#### 6.2.2 监控仪表板配置
创建以下Grafana仪表板：
1. **系统健康总览**：服务器状态、服务可用性、错误率
2. **API性能分析**：接口响应时间、QPS、错误分布
3. **数据库监控**：连接数、慢查询、锁等待
4. **数据同步看板**：同步任务状态、数据量、延迟
5. **业务指标看板**：用户活跃度、搜索量、导出量

### 6.3 告警策略

#### 6.3.1 告警级别定义
- **P0（紧急）**：服务完全不可用、数据丢失、安全漏洞
- **P1（高）**：核心功能受损、性能严重下降
- **P2（中）**：非核心功能异常、性能轻微下降
- **P3（低）**：信息性告警、预期内异常

#### 6.3.2 告警渠道
- **P0/P1告警**：短信 + 电话 + 企业微信/钉钉
- **P2告警**：企业微信/钉钉 + 邮件
- **P3告警**：邮件 + 监控系统内通知

#### 6.3.3 告警规则示例
```yaml
# Prometheus Alertmanager 配置示例
groups:
  - name: talent-platform-alerts
    rules:
      - alert: HighErrorRate
        expr: rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m]) > 0.05
        for: 2m
        labels:
          severity: P1
        annotations:
          summary: "高错误率报警"
          description: "{{ $labels.instance }} 错误率超过5%，当前值: {{ $value }}"

      - alert: APILatencyHigh
        expr: histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m])) > 1
        for: 5m
        labels:
          severity: P2
        annotations:
          summary: "API延迟过高"
          description: "{{ $labels.instance }} API P95延迟超过1秒，当前值: {{ $value }}s"
```

## 7. 日志与追踪

### 7.1 日志分类与级别

#### 7.1.1 日志级别
- **DEBUG**：详细调试信息，开发环境使用
- **INFO**：常规操作记录，如用户登录、数据同步开始
- **WARNING**：预期内的异常情况，如重试操作、降级处理
- **ERROR**：需要关注的错误，如API调用失败、数据验证失败
- **CRITICAL**：系统级严重错误，需要立即处理

#### 7.1.2 日志分类
| 日志类别 | 记录内容 | 保留期限 | 存储位置 |
|----------|----------|----------|----------|
| **应用日志** | 业务逻辑执行过程 | 30天 | 文件系统 / ELK |
| **访问日志** | HTTP请求记录 | 90天 | 文件系统 / ELK |
| **审计日志** | 用户关键操作 | 180天 | 数据库 audit_operation_log |
| **任务日志** | 同步任务执行详情 | 30天 | 文件系统 / 数据库 |
| **错误日志** | 系统异常堆栈 | 90天 | Sentry / 文件系统 |

### 7.2 日志格式规范

#### 7.2.1 统一日志格式（JSON）
```json
{
  "timestamp": "2026-03-20T10:30:00.000Z",
  "level": "INFO",
  "service": "talent-backend",
  "module": "api.talent",
  "function": "search_talent",
  "trace_id": "req_1234567890abcdef",
  "user_id": "user_001",
  "request_id": "req_abcdef123456",
  "message": "人才搜索请求",
  "data": {
    "keyword": "人工智能",
    "school_id": "123",
    "role_type": "professor"
  },
  "duration_ms": 245,
  "status": "success"
}
```

#### 7.2.2 关键字段说明
- `trace_id`：全链路追踪ID，贯穿前端、后端、数据库查询
- `request_id`：单次请求唯一标识
- `user_id`：操作人标识（如为登录用户）
- `duration_ms`：操作耗时（毫秒）

### 7.3 日志收集与存储

#### 7.3.1 架构建议
```
应用层（FastAPI/React） → 本地日志文件 → Filebeat → Logstash → Elasticsearch → Kibana
                              ↓
                            Sentry（错误日志）
                              ↓
                       PostgreSQL（审计日志）
```

#### 7.3.2 配置示例
**FastAPI 日志配置**
```python
import logging
import json_logging
from pythonjsonlogger import jsonlogger

# 配置JSON格式日志
json_handler = logging.StreamHandler()
formatter = jsonlogger.JsonFormatter(
    '%(timestamp)s %(level)s %(name)s %(module)s %(funcName)s %(message)s'
)
json_handler.setFormatter(formatter)

logger = logging.getLogger("talent-backend")
logger.addHandler(json_handler)
logger.setLevel(logging.INFO)

# 中间件添加request_id
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID", str(uuid.uuid4()))
    response = await call_next(request)
    response.headers["X-Request-ID"] = request_id
    return response
```

### 7.4 分布式追踪

#### 7.4.1 追踪场景
1. **用户请求全链路**：前端页面加载 → API调用 → 数据库查询 → 返回结果
2. **数据同步任务**：任务触发 → 数据拉取 → 清洗转换 → 入库 → 索引更新
3. **后台作业**：统计生成 → 快照创建 → 缓存更新

#### 7.4.2 实现方案（可选，第一阶段简化）
- **简单实现**：通过 `X-Request-ID` 在日志中串联
- **完整实现**：OpenTelemetry + Jaeger（后续阶段引入）

## 8. 备份与恢复建议

### 8.1 备份策略

#### 8.1.1 数据库备份
| 备份类型 | 频率 | 保留时间 | 存储位置 | 恢复目标时间 |
|----------|------|----------|----------|--------------|
| **全量备份** | 每日 02:00 | 30天 | 异地存储 / 对象存储 | RTO < 4小时 |
| **WAL归档** | 持续 | 7天 | 本地磁盘 + 异地备份 | RPO < 1小时 |
| **逻辑备份** | 每周日 03:00 | 90天 | 对象存储 | 数据误操作恢复 |

**备份命令示例**
```bash
# 物理备份（pg_basebackup）
pg_basebackup -D /backup/full_$(date +%Y%m%d) -Fp -Xs -P -R

# 逻辑备份（pg_dump）
pg_dump -h localhost -U talent_user talent_db > /backup/logical_$(date +%Y%m%d).sql

# WAL归档配置（postgresql.conf）
archive_mode = on
archive_command = 'cp %p /backup/wal/%f'
```

#### 8.1.2 应用数据备份
| 数据类型 | 备份方式 | 频率 | 保留时间 |
|----------|----------|------|----------|
| **用户上传文件** | 同步到对象存储 | 实时 | 永久 |
| **配置信息** | Git版本控制 | 提交时 | 永久 |
| **静态资源** | 构建产物存档 | 每次发布 | 最近5个版本 |

#### 8.1.3 日志备份
- 应用日志：ELK自动轮转，保留30天
- 审计日志：数据库永久存储，定期导出归档

### 8.2 恢复流程

#### 8.2.1 数据库恢复场景

**场景1：数据误删除恢复**
```bash
# 1. 停止应用服务
systemctl stop talent-backend

# 2. 恢复指定时间点的逻辑备份
psql -h localhost -U talent_user talent_db < /backup/logical_20260319.sql

# 3. 应用WAL日志恢复到误操作前时间点
recovery_target_time = '2026-03-20 14:30:00'
recovery_target_action = 'pause'

# 4. 启动数据库验证
# 5. 重新启动应用服务
```

**场景2：数据库服务器故障**
```bash
# 1. 在新服务器安装PostgreSQL
# 2. 恢复最近的全量备份
pg_basebackup恢复或物理文件拷贝

# 3. 应用所有WAL日志
# 4. 修改连接配置，指向新服务器
# 5. 重启应用服务
```

#### 8.2.2 应用恢复场景

**场景：服务器硬件故障**
1. 在新服务器部署基础环境（Docker、Python、Node.js）
2. 从Git拉取最新代码
3. 从备份恢复数据库
4. 从对象存储恢复用户文件
5. 启动所有服务
6. 验证系统功能

### 8.3 备份验证与演练

#### 8.3.1 定期验证
- **每月**：恢复测试（在隔离环境恢复备份数据）
- **每季度**：完整灾难恢复演练
- **每次大版本发布前**：备份恢复测试

#### 8.3.2 验证检查清单
- [ ] 备份文件完整性和可读性
- [ ] 数据库恢复后数据一致性
- [ ] 应用功能正常
- [ ] 用户权限和配置正确
- [ ] 性能满足要求
